# libsodium code generation

This development-only Python project generates the committed NIF sources, Erlang
modules, Common Test suite, `ex_doc.config`, and `README.md` for libsodium.
Normal `gmake` and `rebar3` builds use the generated files and do not need
Python.

Requires Python 3.13 or later and Poetry 2.1 or later with the
`poetry-plugin-export` plugin.

From the repository root:

```sh
just lock       # Refresh poetry.lock and exported requirements.txt
just codegen    # Render, format, build, render docs, and sign generated sources
just format     # Format C, Erlang, templates, and Python sources
```

`just docker-codegen` runs generation in a Linux image built by
`just docker-build` and produces the same files as a native run. The image
caches the locked Python dependencies separately from the host's `.venv`,
builds libsodium inside the container, and removes its Linux build outputs from
the shared work tree afterwards. Docker helpers also cover formatting, locking,
signing, and an interactive shell.

## Stages

`just codegen` runs these steps:

1. `templates0/` renders the native sources under `c_src/nif/`, every Erlang
   module under `src/`, `test/libsodium_api_SUITE.erl`, and `ex_doc.config`.
   Templates whose path contains `[namespace]` or `[module]` render once per
   namespace.
2. The generator scans `c_src/nif/` for literal `ATOM(name)` references and
   renders the atom table from `templates1/`. Explicit atoms in `config.yaml`
   are always included.
3. `clang-format` and `erlfmt` format the outputs, and `gmake` builds the NIF.
4. `templates2/` renders `README.md` against the built library. It uses the
   `~J{ ... }.` and `~J< ... >.` delimiters of the Erlang templates;
   `erlang("Expression")` inserts an Erlang term, and the `"hex"` and `"text"`
   formats insert a binary as hexadecimal or as text. Every `erlang` code block
   then runs with fresh bindings; a failure prevents the README from changing.
5. Every generated file is signed. The signature covers the formatted content,
   and repeated generation is stable.

To check the committed README without changing it:

```sh
gmake
cd codegen
poetry run erlang_libsodium_codegen generate --stage docs --check config.yaml .. templates0 templates1 templates2
```

## Namespace definitions

`config.yaml` holds global NIF settings. Each libsodium namespace is defined in
`namespaces/<namespace>.yaml`; `schema.json` and `namespace.schema.json`
(regenerated by `just codegen`) describe both formats, and
`src/erlang_libsodium_codegen/schema.py` is authoritative.

```yaml
crypto_secretbox:
  title: Secret-key authenticated encryption
  doc: Markdown module documentation.
  example: |
    Key = libsodium_crypto_secretbox:keygen(),
    ...
  constants:
    - name: keybytes            # crypto_secretbox_keybytes()
      value: 32                 # checked by the generated tests
  functions:
    - name: easy
      doc: Encrypt and authenticate `M`...
      args:
        - {type: binary, name: m}
        - {type: fixed, name: n, size: crypto_secretbox_NONCEBYTES}
        - {type: fixed, name: k, size: crypto_secretbox_KEYBYTES}
      outputs:
        - {name: c, size: "mlen + crypto_secretbox_MACBYTES"}
      returns: c
  tests:
    - name: round_trip
      code: |
        ...
```

Each function becomes `libsodium_nif:<namespace>_<name>/<arity>` and one or
more clauses in the public module (`libsodium_<namespace>` unless `module` is
set). `erlang` variants map public parameters onto native arguments, which
supplies defaults such as empty additional data.

Arguments decode Erlang terms into C locals:

| Type | Erlang term | C locals |
| --- | --- | --- |
| `binary` | any binary (optionally `min`/`max`, `nullable`) | `x`, `xlen` |
| `fixed` | binary of exactly `size` bytes | `x` |
| `cstring` | binary without NUL bytes | `const char *x` |
| `state` | state resource of `c_type` | aligned copy `c_type x` |
| `uint` / `int` | integer within the C type's range | `x` |
| `enum` | atom (or its integer value) | `x` |

Outputs are allocated binaries (`buffer`), states, or scalars. The call
defaults to the libsodium function with outputs first and binaries as pointer
and length; set `call` when the signature differs. `returns` names outputs, uses
`uint:`, `int:`, `atom:`, `atom_cstr:`, or `string:` expressions, or lists items
for a tuple.

States are NIF resources, one resource type per C type
(`c_src/nif/core/libsodium_nif_state.c`), exposed as opaque
`libsodium_nif:<c_type>()` types and aliased as `state()` in each namespace
module; a namespace may use only one state type. A call copies an argument
state into an aligned local and returns any resulting state as a new resource,
so states are never modified once Erlang can see them.

Invalid arguments raise `badarg`. With the default `check: zero`, a non-zero
libsodium result is returned to Erlang as that integer, as the port driver did.
Buffers are wiped before release, and argument states and C strings are wiped
after each call.

## Scheduling

With the default `schedule: auto`, a call whose binary inputs (plus integer
arguments marked `work: true`) exceed `nif.dirty_threshold` bytes reschedules
itself onto a dirty CPU scheduler. `dirty_cpu` and `dirty_io` always run dirty;
`normal` never does. Functions marked `update: true` absorb a binary into a
copy of a state in `nif.update_chunk` byte chunks and yield whenever the timeslice is
exhausted (`c_src/nif/core/libsodium_nif_update.c`).

## Tests

Recorded constants, each namespace's `example`, and its `tests` run in the
generated `test/libsodium_api_SUITE.erl`. Run the generator's own checks with
`cd codegen && poetry run pytest`.
